## See Reedwork in action

Reedwork lets you define a command without manually constructing or registering a Brigadier command tree.

```java
@Command("hello")
public final class HelloCommand {

    @CommandHandler
    public boolean execute(CommandContext context) {
        context.player().sendMessage(
            Component.text("Hello, Reedwork!")
        );

        return true;
    }
}
```

The command is discovered and registered automatically when your plugin scans its components.

You can add metadata such as a description, permission, cooldown, aliases, or an explicit usage when needed.

If no usage is specified, Reedwork generates it automatically from the command structure.

## How Reedwork works

Reedwork does not impose a separate application architecture on your plugin.

Instead, it provides the infrastructure around your existing Paper components:

<Steps>
1. **Discover**

   Reedwork scans your plugin package and discovers supported components such as commands, event listeners, and services.

2. **Resolve**

   Dependencies are resolved automatically through Reedwork's dependency injection system.

3. **Register**

   Reedwork connects the discovered components to the appropriate Paper systems.

   Commands are registered as Brigadier command trees, event listeners are registered with Bukkit/Paper, and registry-backed components are created during the appropriate Paper lifecycle phase.
</Steps>

## Dependency injection without the boilerplate

Dependencies are resolved automatically, allowing your plugin components to remain focused on their actual responsibilities.

```java
@Command("hello")
public final class HelloCommand {

    private final GreeterService greeterService;

    public HelloCommand(GreeterService greeterService) {
        this.greeterService = greeterService;
    }

    @CommandHandler
    public boolean execute(CommandContext context) {
        greeterService.sendGreeting(context.player());
        return true;
    }
}
```

No service locator.

No manual wiring.

Just constructor dependencies.

Reedwork can manage components as singletons or transient instances, while external classes can be registered through explicit bindings.

## Built on Paper

Reedwork does not replace the Paper APIs you already know.

Your event listeners are still Bukkit/Paper listeners.

Your commands are still Paper Brigadier commands.

Your enchantments are still integrated through Paper's registry system.

Your services are still ordinary Java classes.

Reedwork simply removes the repetitive infrastructure connecting these pieces together.

## The Reedwork approach

**You define what your plugin needs. Reedwork handles how those components are discovered, created, and registered.**

This keeps your plugin code focused on behavior instead of framework infrastructure.
